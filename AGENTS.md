# Knowledge bank operating contract

## Public repository

This repository is public. Before every commit, review the full staged diff and newly added files for private information. Remove or anonymize credentials, private correspondence, personal contact or account details, and nonpublic employer or customer information, including internal access and deployment details. A secret scan supplements this review; it does not replace it.

Personal preferences and personal project notes are intended to be public. Keep raw session histories, browser captures, local runtime state, and private backups out of commits. If it is unclear whether a detail may be shared, ask Tobias before committing it.

## Using retrieved knowledge

Use retrieved knowledge to shape the answer, not merely list what you found. Personal global instructions own retrieval before substantive work across repositories.

Use the request and relevant vault knowledge to establish the intended outcome, important constraints, and what would demonstrate success. Let these guide further retrieval and execution. Resolve what you can from existing context; make consequential assumptions visible and ask about gaps that could materially change the result. Preserve the goal, settled decisions, and completion criteria through context changes and handoffs. See `[[Prompting tool-using agents]]` when the task contract needs clarification.

`[[index]]` is orientation, not an exhaustive map: absence from it means nothing, and agents must search. `[[Projects]]` provides repository and project routes.

## Maintaining knowledge

This is a public, subject-centered living Markdown knowledge bank. Preserve reusable findings from work, experiments, research, Pi/Codex histories, project thoughts, and personal memories only when suitable for public sharing. Search first, then integrate into an existing note when possible; revise and compress actively. Use human-readable filenames and meaningful Obsidian `[[wikilinks]]`. Folders and conventions may evolve. Do not add mandatory frontmatter or note types.

Promote knowledge that can change how future agents understand, decide, or act: findings, useful failures, rationale, procedures, corrections, preferences, and worthwhile hypotheses. Treat stored claims as current working knowledge and state them directly; proof, citations, confidence labels, evidence-limit sections, and research methodology are not defaults. Verify and revise when Tobias, another agent, new evidence, or changed conditions challenges a claim. Keep provenance only when source authority, volatility, conflict resolution, exact measurements, or consequences make it useful. Optimization claims retain baseline, change, effect, conditions, and tradeoffs. A knowledge note is not a research report, bibliography, or speculative guide: prefer conclusions and useful distinctions over research trails, and keep procedures only when they are established and reusable. Untested proposals belong only to active project work. Exclude routine activity, generic summaries, and cheaply rediscoverable detail. Never store secrets.

`[[conflicts]]` is an active queue. Version, date, environment, and scope distinctions are scoped differences rather than contradictions. Auto-resolve contradictions only for explicit supersession by the same authority or verified transcription/citation errors. Human review is required for other conflicts; remove a resolved queue entry after updating living notes.

`[[Knowledge consistency]]` is the canonical policy for materially duplicated and contradictory knowledge. Use `.agents/skills/audit-knowledge-consistency/SKILL.md` only when the user explicitly requests a consistency audit or consolidation. Audits are read-only. Explicit consolidation authorizes safe merges within the stated scope, but not ambiguous conflict resolution, whole-note deletion, substantial deletion, or broad restructuring. Note age, missing dates, elapsed time, and schedules never trigger this workflow.

In ordinary conversation, suggest and ask before saving. An explicit save or consolidate request authorizes relevant edits. History review presents candidates and waits for approval. Promotions to AGENTS behavior, broad restructuring, and substantial deletion require approval. One writer edits; read-only parallel analysis is allowed. Report changed notes. Never commit unless asked. Git is passive local history and changes remain uncommitted.
