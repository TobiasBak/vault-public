# One blocking gate for agent-written code in any language

Status: v1 built; all five build steps and the two-layer suite landed (2026-11-05); corpus acceptance and calibration done (2026-11-06).

recheck-after: 2027-02-06

## Abstract

Existing linters stop at one language, and agents erode codebases in ways that are not tied to any language: they add code beside old code, cross boundaries, swallow errors, pile defensive checks onto guaranteed types and loosen their own gates. This paper designs a single Linux binary that checks those problems from one set of rules, starting with Rust, Python and TypeScript, configured per repository, with every finding blocking. It claims that most of the erosion agents cause is visible without a type checker, in a language-neutral model of definitions, imports, references and calls. The tool is also the apparatus for the gate hypotheses in the [codebase erosion paper](agent-codebase-erosion.md).

## Thesis

A language-agnostic, always-blocking gate built on syntax trees can catch most of the erosion agents cause, with false positives rare enough that repositories keep every suite rule on.

The thesis is refuted if concept rules miss or misfire materially more often than the per-language tools they replace, if unresolved sites swamp real repositories, or if repositories disable large parts of the suite to stay usable.

## Capabilities

Each capability exists because agents reliably produce the failure it blocks. Capabilities are anti-patterns, and anti-patterns do not depend on language: the suite's generic rules are one rule per anti-pattern, which riprap applies to whichever languages the candidate contains. Problems that exist in only one language live in that language's group, which extends the generic rules and applies whenever the candidate contains the language. Only decidable checks become rules. A heuristic, such as a new path landing beside an old one or a new symbol resembling an existing one, appears in `report` until it is narrowed into something decidable.

### Accretion

Agents add code and rarely delete it. This is the core of the tool.

- Unused exports, files and dependencies.
- Names like `*_v2`, `new_*`, `legacy_*`, `utils2` and `helpers/` on files and directories. On definitions only `_v2` and `utils2` hold: every `legacy_*` and `new_*` definition in Tobias's repositories was a real name, compatibility handling or a creation verb.
- Exact clones: production functions whose syntax trees match once names are numbered by first use and literals reduced to their kind, at 50 or more body tokens. Tests, trait-impl members and parameterizations are excluded: branch-free functions whose body is one call, preceded only by plain bindings of names the rest of the body uses, with no method chain anywhere.
- Repeated literals: a module-level constant defined in two files of one language, either a distinctive string of eight or more characters or a same-named number above 10 that is neither round nor a power of two.
- Forwarding wrappers: a parameterization that adds no arguments, so its whole body passes its parameters, receiver included, unchanged and in order to one call that resolves to a production function; and a Python or TypeScript class whose every method does that to one field. Constructors, chained receivers and foreign targets do not forward. A public function of one layer forwarding into another, a public function that gives a type an operation it cannot re-export, entry points, functions an attribute or decorator registers, imposed signatures and callbacks pass. Rust impls stay out of the class form, because a newtype's delegating impl is how a wrapped type gets its own name.

### Boundaries and ownership

- Imports between layers along an edge the config does not declare.
- Import cycles between modules.
- Reaching into another module's internals instead of its public entry point.
- Test-only hooks in production code.
- Dispatch on strings outside a boundary: three or more branches that compare one value against identifier-like literals, or assign one state variable three or more of them in one chain, when most of those strings recur elsewhere in production code. A branch compares by equality, by Python membership in a literal tuple, list or set, or through one side of an `and` or `or`, and consecutive `if` statements without `else` count as one chain. A match whose every arm builds a typed value is a decoder and passes, as does a TypeScript switch over a declared union of literal types and a Python attribute hook such as `__getattr__`.
- Literal boolean arguments: a bare `true` or `false` passed by position to a production function whose parameter there is declared boolean. Calls resolve by name, to the caller's file first for an unqualified call, to the named type for a path call and among methods for a call on a value; when the reachable functions disagree the call does not resolve. Keyword arguments, foreign functions and a `set…` setter whose only boolean parameter comes first pass.
- Needless exports: a public Rust function, method or constant in a library another package of the repository depends on, which production code uses but nothing outside its crate uses, and an exported TypeScript value only its own file references. Types stay exported, because a public signature may need them. Binary-only crates pass, since `pub` there reaches nothing beyond the crate. In Rust a use is a path, call, method call, import, attribute or macro argument naming the item; a same-named local, field access or string literal is not. A `$crate::` path in a `#[macro_export]` macro's body is a use from outside the crate, because the expansion runs in the invoking crate. Python has no export to narrow: `__all__` appeared in 2 of about 580 production modules and the underscore convention was used inconsistently, so the cell is not applicable.
- String errors: a failure no caller can match by type. In Rust, a function in a library target returns `String`, `&str`, `Box<dyn Error>` or anyhow as its error. A lib target counts when its package has no binary and does not set `publish = false`, or when another package depends on it as a normal dependency, and that package is not a development tool: `xtask` by name or a cargo-fuzz package by manifest metadata. anyhow stays free in applications and in unpublished libraries that only tools, build scripts and tests use, because those callers only print the error. In Python and TypeScript, a named function outside every boundary raises a bare `Exception` or throws a plain `Error` or a string. Module-level script code, callbacks written inline in a call and tests pass.

### Defensive slop

- Swallowed errors: a catch-all `except: pass`, an empty `catch {}`, and in Rust a discarded `Result` (`let _ =`, a statement-level `.ok()`, an `unwrap_or` that ignores the error) when a repository signature or a known standard call shows the value is a `Result`.
- Catch-all handlers that log and continue.
- Fallback defaults on decoded data: `?? default`, `.get(k, {})`, `unwrap_or_default()`.

### Over-engineering

Agents cover edge cases the types already exclude, with fallback on fallback and checks repeated deep inside code that should trust its inputs.

- Type checks an annotation already guarantees: `isinstance(x, int)` when `x: int`, `typeof x === "string"` when `x: string`, `if x is None` when `x` is not optional.
- Error handling outside a boundary, `catch_unwind` included. Cleanup inside a Rust `Drop`, which cannot propagate, passes, and so does a handler that records the failure on a collector its caller passed in, such as a `&mut` parameter or a Python or TypeScript parameter it appends to; recording on `self`, a global or a logger still hides the error.
- Never-failing wrappers: a function that declares failure or absence and succeeds on every path. In Rust every exit is `Ok(…)` or `Some(…)` with no `?`, `Err`, `None`, `bail!` or `ensure!` in the body; in Python and TypeScript every return is a value that cannot be None, null or undefined and the end is unreachable. Implementations, overrides, cfg-gated and registered functions, callbacks and `todo!()` bodies pass.
- Lonely abstractions: a trait, interface, `Protocol` or ABC that declares methods and has exactly one implementation, tests included. Blanket, generic and macro-expanded impls stand for many types; an extension trait on a foreign type that no bound names, and an abstraction a layer defines for a layer it may not import, pass because removing them is impossible or would break a layer edge.
- Useless handlers: a catch that only rethrows, a `try` nested inside a handler, a handler that returns a default.
- Fallback chains of three or more: `a ?? b ?? c ?? d`, `x or y or z or {}`, `getattr(o, "k", None)` on a typed object.

Handler density per thousand lines is a report-only metric in `report`.

### Structure

- Long parameter lists: six or more parameters a caller must supply, with Python keyword-only parameters counted, a tuple pattern or a tuple of differently typed values counted once per element, and parameters with defaults, the receiver and a UI framework's window and context handles left out. Imposed and registered signatures, callbacks and anonymous functions pass.
- Primitive aliases: a type alias that renames a bare primitive or string type, such as `type NodeId = String`. Generic aliases, aliases of other types, unions of literal types and associated types in trait impls pass.
- Anonymous tuples: a tuple of three or more fixed elements in a parameter or return type, nested inside a generic or not. Implementations of a trait, interface or base class, callbacks, variable-length tuples, Python stub files and comparison keys pass; a comparison key is a function whose name ends in the word `key`, `rank` or `identity`.

### Unfinished and leftover code

- Stubs: `todo!()`, `unimplemented!()`, `raise NotImplementedError`, a function whose body only passes.
- Debugger calls: `breakpoint()`, `pdb`, `debugger`, `dbg!`.
- Disabled code: `if False:`, `if (false)`, dead branches behind constant conditions.

### Tests that lie

- Mocks of the repository's own modules.
- Sleeps and real timers in the test's own control flow. A sleep in a closure, lambda, nested function or async block the test hands on, such as a fake's handler or a spawned producer, simulates latency and passes, unless that block asserts and so carries the test itself.
- Snapshot and golden-file assertions.
- Tests reading private state.
- Skipped tests: `.skip`, `xfail`, `#[ignore]`.

### Comments

A comment that explains a workaround or justifies the code usually marks a design heading the wrong way, and the next agent copies both. The message steers toward names and types, a check that carries the reason, or an ADR. Reasoning in [documentation and naming](../agents/documentation-and-naming.md).

- Line and block comments.
- Docstrings and doc comments.
- Suppression directives such as `noqa` and `@ts-expect-error`.
- Not a shebang, or one `SPDX-License-Identifier` line at the top of a file.

### Dependencies

- A dependency imported directly that the manifest only has transitively.

### Hygiene

- JavaScript files: TypeScript only. A repository whose runtime mandates JS disables the rule; a single served script becomes an out-of-scope path.
- READMEs anywhere and nested agent instruction files. Docs directories are allowed.
- Committed binaries, decided by executable signature: ELF, Mach-O, PE, ar, WebAssembly, Python bytecode. Images and other assets never match.
- Oversized fixtures: at least 128 KiB and compressing at least 64-fold. Real inputs in Tobias's repositories compress under 40-fold.

### Ratchets

- A metric above its ratchet: the value committed in the config or, when the config commits none, the metric's default. Clone lines, complex-function mass, nesting excess and file excess default to 0, because each sums erosion; non-leaf excess has no default. A committed ratchet's finding sits on that value's line in `riprap.toml`; a default's sits on the largest contributor. Either lists the metric's top contributors, because a ratchet promises something about the whole codebase and any single contributor may be untouched old code. A repository adopting riprap commits its current values and lowers them as the code improves.

The metrics `report` prints. Only a metric that deleting a function cannot raise carries a ratchet: an absolute sum of something bad in itself. A ratio with production lines underneath rises whenever simple code is deleted, so ratios are report-only, and `riprap.toml` refuses a ratchet on them.

- **Clone lines,** ratchetable: production lines in functions that copy an earlier function.
- **Complex-function mass,** ratchetable: cyclomatic complexity times the square root of lines, summed over production functions above complexity 10.
- **Nesting excess,** ratchetable: how far each production function's deepest control-flow nesting goes beyond 3, summed. `else if` does not nest, and closures and nested functions add depth to their enclosing function rather than counting on their own, so unwrapping one cannot raise the sum.
- **File excess,** ratchetable: production lines beyond 600 per file, summed. Blank and test lines do not count.
- **Non-leaf excess,** ratchetable: lines in branching production functions beyond 25 per non-leaf module, summed. A non-leaf module is a Rust file that declares file-backed child modules, `lib.rs` included, a Python `__init__.py` or a TypeScript `index.ts` beside sibling modules. Straight-line composition, such as a router that mounts its children's routers, is glue and counts at no length. It measures a layout policy rather than erosion, so it ratchets instead of blocking, and only when the config commits a value.
- **Complexity density,** report-only: total cyclomatic complexity per thousand production lines.
- **Handler density,** report-only: production error handlers per thousand production lines.

## Design

### Shape

One static Linux binary, `riprap`, named for the rock armour that stops shoreline erosion. `check` judges a candidate and exits nonzero on any finding. `test` runs every rule's examples. `report` prints metrics and never fails. Formatters and type-aware linters stay separate tools; the repository's landing command runs them beside riprap.

Exit codes: `0` passes, `1` has findings, `2` means riprap could not run, for example on an invalid config, a rule that fails to decode, or a file it cannot parse. Each finding is one line naming the rule, `path:line:col`, the message and the approved path; `--json` gives the same for tools.

### Implementation language

Rust, because the hard parts already exist as Rust libraries and the tool must ship as one fast binary.

- Tree-sitter's best-maintained bindings and the grammar crates compile straight into the binary, and `ast-grep-core` supplies matching for language rules.
- A native binary has no runtime to install. mise installs it from the repository with its cargo backend; prebuilt binaries wait until a second machine needs them.
- Parallel parsing without garbage-collection pauses fits the speed target, as Ruff, Biome, oxc and ast-grep show.
- Rule files and config decode once through serde into types with no invalid states. With no severity field in the type, a warning level cannot exist.
- Rust is among the first adapters, so the tool gates its own source early.

The cost is compile time in the agent's own edit loop. Split the workspace so a rule change never rebuilds the parser, and keep a warm [target cache](../software/cargo-target-cache.md).

Extending the tool never requires Rust. Rules and config are TOML, and adapters are mostly tree-sitter query files in the style of `tags.scm`, with Rust only where a language's name resolution needs real code.

### Model

Adapters built into the tool parse with tree-sitter and map each language into one model: files and modules, definitions and exports, imports and references, calls, error handlers, tests, comments and literals. Adapters also carry language meaning for shared concepts, such as what an ignored error or a sleep call looks like in that language. Adding a language means writing one adapter; no rule changes.

v1 has adapters for Rust, Python and TypeScript including TSX. Resolution understands Cargo workspaces, uv projects and workspaces, and TypeScript's `tsconfig` paths, pnpm workspaces and `package.json` exports, following re-exports through barrel files. Other layouts are unresolved until an adapter learns them.

riprap does not duplicate the compilers. rustc already flags dead private code and `tsc` flags unused locals, so riprap covers what they cannot see: exports unused across the workspace, unused files and dependencies, and in Python, which has no compiler, private dead code too.

### Rules

Three kinds, available to the suite and to repositories alike:

- **Violation rules** produce findings. The suite has two layers. A generic rule names an anti-pattern that exists in more than one language; its id, message and approved path carry no language, and its language-specific shapes are conditions inside it, one per language, each an ast-grep condition or a model concept. Adding a language adds conditions, and one disable turns the anti-pattern off everywhere. A language group, one per language, holds language rules for problems only that language has, such as mutable default arguments in Python, `as any` in TypeScript or `#[allow]` in Rust. A group adds rules on top of the generic ones and never changes them. A repository's own rules may be either kind. One crate owns the ast-grep dependency and speaks riprap's own types, so replacing ast-grep later touches only that crate.
- **Coverage** is explicit for generic rules. For each anti-pattern and language, the rule either covers it, declares it not applicable with a reason, such as `except` in Rust, or leaves it unbuilt, and `riprap test` prints the matrix, so a gap is a visible cell rather than a missing file.
- **Fact rules** add references or entry points to the model, so a repository's own dynamic patterns, such as a handler registry looked up by string, become visible to rules that read the graph. The suite ships fact rules for the frameworks in use, starting with pytest fixtures.
- **Config** declares layers and the edges between them, boundaries, entry points, out-of-scope paths, parameters and ratchet values.

Every rule file carries examples that must flag or pass, and fact rules prove the references they add. Syntax rules and comment cells can use snippets; concept cells that read the graph use file trees. `test` rejects any disagreement between the rule and its examples.

A language rule or one covered cell can narrow its findings with `paths`, a nonempty list of globs rooted at the repository, without removing those files from the shared model or changing another rule. This is rule applicability, not a per-file suppression. A scoped rule needs trees proving both an included finding and excluded code that the same rule would flag without its path scope. Pathless snippets still prove syntax as covered code, with companion trees proving scope. riprap's `AGENTS.md` owns the authoring format.

A rule joins the suite only after a run across Tobias's repositories in which every finding is a real problem. One false positive means narrowing the rule first. Real findings are not a blocker; each repository fixes them when it upgrades riprap.

### Blocking

- The rule format has no severity field. A finding always fails `check`.
- No inline or per-file way to silence a finding exists.
- A file riprap cannot parse means riprap could not run: exit 2, naming each file and position, never a skipped file, so broken or unsupported syntax cannot hide code from the rules. riprap cannot tell a grammar gap from truly broken syntax, and the compiler catches the latter anyway. Vendored code that hits a gap becomes an out-of-scope path.
- An unresolved site is a finding when the construct is avoidable: a computed `getattr` or `importlib` name, a non-literal `import()`, `eval`. The approved paths are an explicit registry, a fact rule or a declared entry point. Language machinery that cannot be avoided, such as Rust macros, Python decorators and barrel re-exports, resolves conservatively: whatever it names counts as used, which may miss dead code but never invents a finding.
- A repository can disable a rule only as a whole, with a required reason, which stays visible in every diff of the config. Catching a loosened config is the developer's job in review, not riprap's.

### Config

`riprap.toml` in the repository root records every difference from the suite: the repository's rule directory, overrides of suite rules by id, disables with reasons, parameters, layers, boundaries, entry points, out-of-scope paths and ratchets. Out-of-scope paths are exact, never globs, so the scope cannot quietly widen.

The binary ships only the current suite. A repository's pinned riprap version in `mise.toml` is its suite version, so upgrading means bumping the pin and fixing what the new rules find in the same change.

### Candidate

`check` judges the whole tree, always: the working tree, which is the candidate in a gah workspace, or the index with `--staged`. There is no diff mode. Old findings in untouched code are still findings, and graph rules cannot be judged from a diff anyway: deleting the last caller of an export leaves the unused export in a file the diff never touched.

### Speed

A whole-tree check of orderready, about 640k lines of Rust, must finish in under a second warm, with files in the page cache and no persistent cache. A cache that gives the same result as a full run is added only if a measured run misses that.

## Build order

1. The comment rule, so riprap gates its own source from the start.
2. Language rules through ast-grep: defensive slop, over-engineering, leftovers and tests that lie.
3. The model and graph: unused code, boundaries, cycles, internals access and error handling outside boundaries.
4. Banned names and hygiene.
5. Exact clones, metrics and ratchets.

## Hypotheses

1. **Concept rules match per-language tools.** Unused-export, dead-file and boundary results agree with knip, vulture and import-linter on real repositories, except where code is dynamic. Refuted if disagreement outside dynamic code is common.
2. **Unresolved sites are rare.** On typical Python and TypeScript repositories, they number few enough to fix with fact rules or entry points in one sitting. Refuted if they swamp the real findings.
3. **The suite stays quiet on good code.** On well-maintained repositories, nearly every finding is judged real. Refuted if a rule's false positives would push a repository to disable it.
4. **Agents write correct rules in one pass.** Given a real mistake and its fix, an agent writes a rule whose examples pass and which rejects the original failure. Refuted if most attempts need human repair.
5. **Whole-tree checks are fast enough for every commit.** The orderready target above holds. Refuted by measurement under the [benchmark checklist](../skills/benchmark-checklist/SKILL.md).
6. **Blocking without silencing is livable.** Agents fix findings rather than loosening the config. The test belongs to hypothesis 6 of the [erosion paper](agent-codebase-erosion.md).

## Method

1. Compare graph rules against knip, vulture and import-linter on a handful of public repositories per language, and inspect every disagreement.
2. Run the suite on the reference corpus and on Tobias's 12 repositories, and judge findings real or false, at least 10 per rule and class. The corpus, `corpus/corpus.toml` in riprap, pins 34 public repositories by commit in three classes: agent-written by their own documentation or by benchmark origin, well-maintained, and ordinary. It is the basis for acceptance and calibration: every rule change lands with its effect on the corpus and on Tobias's repositories, and a threshold must separate agent-written from well-maintained code or be kept as stated policy. Rules that only run under a declaration, such as layers and boundaries, run with a real declaration where one exists and elsewhere with a stand-in written from the repository's real structure, its entry points, generated files and layers; an undeclared repository proves nothing about them, and a blanket boundary proves little.
3. Replay recorded agent mistakes from review history: an agent writes the rule, and the rule must reject the historical change and pass the fix.
4. Time `check` on orderready, warm and cold.

Follow the [fast-loop funnel](../agents/autoresearch.md#fast-loops-first-tobias-2026-10-12): scout each measurement on one or two repositories and widen only where the signal is clear.

## Results

Build step 1, 2026-11-05: a release build checked orderready's whole tree, 2,389 Rust files and about 640k lines, in 0.346 s wall on one warm run without a cache, on a shared Ryzen 7 7800X3D with 16 threads under load average 2.4. One run, so no variance figure. tree-sitter-rust 0.24.2 failed on four valid files under `third_party/`, among them `dyn 'static + FnOnce()`, which led to parse failures exiting 2 instead of being findings.

Build step 2, 2026-11-05: 31 language rules joined the comment rule. Each had zero false positives in an acceptance run across Tobias's 12 repositories, judged by the building agent under his standards. Getting there took narrowing: `except: pass` counts only catch-all handlers, `.get(k, {})` only chained with a literal key, `unwrap_or_default()` only after a JSON accessor. Plain `print` and `console.log` were dropped because every hit was a script's real output. The same orderready check took a median of 387 ms over 10 warm runs (376 to 427 ms) on 16 threads, against 320 ms for the comment rule alone, so one shared walk for all language rules costs about 65 ms. Parsing each file once matters more: in the `patterns` measurements a second parse cost about three times the whole matching walk, and walking once per rule cost about 330 ms per rule.

Build step 4, 2026-11-05: seven path rules over every file, with examples written as small file trees. All had zero false positives across the 12 repositories; the counts are mostly READMEs, 187 of them. orderready stayed at 403 ms. omarchy, which carries 190 MB of media, went from 43 to 153 ms because the binary check reads each file's first bytes in sequence.

Build step 3, 2026-11-05: the model and graph, with cross-file resolution for Cargo workspaces, uv projects and TypeScript paths, workspaces and barrels. Usage in Rust and Python is matched by name, which gives up some recall to avoid false positives. Decorators and macros count as machinery, treated as used until a fact rule resolves them; pytest fixtures, autouse fixtures, hooks and Nautilus extensions ship as fact rules. Across the acceptance run every finding was judged real: 129 mocks of the repository's own modules, 60 test-only hooks, 44 unused definitions, 19 unused and 11 transitive dependencies, 7 unresolved sites, 4 internals accesses, 2 unused files and 1 test nothing starts. Rust import cycles were dropped because module cycles are legal Rust. Layer and boundary rules were proved on fixtures only, because no repository declares layers yet.

Hypothesis 1, first evidence: on six Python repositories vulture reported 694 items. riprap flagged 17 of them and nothing vulture missed. Of the rest, 343 are outside riprap's scope, such as attributes and locals, 317 are framework or test code that riprap correctly keeps, and 17 were cases where riprap was right on inspection, such as names used only from strings. One was a real miss: a dead helper in a unittest subclass, which riprap keeps because it treats every method of a class with an external base as a possible override.

The orderready check grew to a median of 685 to 776 ms against 406 to 414 ms for the step 4 binary, over three interleaved rounds of 11 warm runs under load average 1.8 to 5.7 from other agents. An instrumented run split the time into about 360 ms parsing and inspecting files, 95 ms building the graph and 45 ms in concept rules. It is under the one-second target, so no cache was added.

Build step 5, 2026-11-05: exact clones, repeated literals, `report`, ratchets and a speed pass. Both new rules had zero false positives across the 12 repositories after narrowing. Clones stopped flagging enum-to-string tables, `get` and `get_mut` twins, trait delegations and tests. Literals had to drop raw occurrences, which numbered in the thousands, coincidental numbers with different names, round numbers and comparisons across languages. orderready's real findings were mostly one colour and type-scale palette copied into about five UI modules. Metric values across the repositories ranged from 0 to 4.75 for clone share, 29 to 86 for concentrated complexity and 1.3 to 17 for handler density. riprap commits its own values as its first ratchets.

The orderready check settled at a median of 635 ms, with 6.6 s of CPU, under load average 6 to 9. Parallel file reads, query compilation and rule execution won back about 140 ms, and the new features cost about 74 ms. The check is now bound by tree-sitter parsing, which takes about 40 percent of the CPU, the model query and ast-grep, so the next large gain needs a cache or less parsing. omarchy measured 693 ms before the speed pass and 217 ms after; step 3's mention building over its 66 MB of text was serial, which made step 4's 153 ms figure stale.

Two-layer suite, 2026-11-05: per-language twins such as `swallowed-error-python` merged into generic rules, with findings identical apart from ids on all 12 repositories. The coverage matrix has 90 cells: 80 covered, 7 not applicable for Rust with reasons, such as import cycles and redundant type checks, and 3 not built, which are Rust swallowed errors and private state in tests for Rust and TypeScript. New cells and rules all passed acceptance: a handler that only returns a default in all three languages, Rust log-and-continue limited to logging then `continue`, Rust rethrow-only limited to tail matches that `?` can always replace, and language-group rules for Python mutable defaults, TypeScript `any`, Rust `.unwrap()` in production code and `#[allow]`. `#[expect(lint, reason = ...)]` stays allowed: git-at-home bans process calls workspace-wide through Clippy's `disallowed_methods` and its owning module expects the lint with a reason, so the attribute marks a declared owner rather than a silenced problem, and it fails once the lint stops firing. Production-only rules exempt poisoned locks, panicked threads and literal parsing; `.unwrap()` hits on orderready dropped from 487 to 0 once test modules were recognized. Clones, literals and metrics now count production code only. A complexity-density metric, total cyclomatic complexity per thousand production lines, joined the report, ranging from 120 in orderready to 509 in pi-workspace-view. riprap declared its own layers and boundaries: zero layer-edge findings, and removing one declared edge produced seven, which proves the rule on real code. The orderready check measured 507 ms against 492 ms before.

First adoption, orderready, 2026-11-06: 309 findings in 2,911 files with no declaration, mostly READMEs (103), repeated literals (62), test-only hooks (50), unused definitions (25), exact clones (22) and unused dependencies (20); spot checks found them real. The count hid the architecture rules, which stay silent until riprap.toml declares layers and boundaries. Declaring orderready's real layers from its ADRs and crate graph exposed that both rules had passed acceptance without ever running on real code. layer-edge reported 24 findings, all test files importing a dev-only testkit; it now judges production code only. handler-outside-boundary reported 263, most of them handlers that recover one specific failure while the others propagate, or that keep the error in a typed result, which riprap's own handler-returns-default rule tells agents to write. It now flags only catch-all handlers outside a boundary that neither propagate nor keep the error, nor return a Rust `None` the signature declares, and orderready dropped to 83, all log-only handlers, discards and substituted fake values, all judged real. The acceptance repositories without declarations showed no change, and nine of them under a stand-in declaration lost findings only. The orderready check went from 510 to 530 ms. Docs directories left the suite on Tobias's decision. Deleting riprap's simple docs-directory rule then pushed concentrated complexity, then a share, from 35.26 to 35.30, past its ratchet, because the denominator shrank; the agent split a function to get back under. Ratchets now apply only to absolute sums, clone lines and complex-function mass, and a test proves deleting a simple function never raises either. A pure deletion can still raise one honestly: removing the one line that told two functions apart creates a clone, and removing a `#[cfg(test)]` marker moves code into production. orderready's values are 299 clone lines and a mass of 45,867.

Second adoption pass, orderready, 2026-11-06: two findings were false positives. sleep-in-test flagged a fake server's handler sleeping to simulate a slow dependency, and exact-clone flagged two public lookups that pass different literals to one shared helper. The first narrowing of sleep-in-test, which exempted every nested closure, also dropped a real wait in dev-loop-lab: a nushell test whose body runs inside a `Playground::setup` closure and sleeps so file times differ. Assertions told the two apart. Across the 12 repositories, with dev-loop-lab's one unparseable vendored file declared out of scope, exactly those two findings disappeared and none appeared; orderready went from 94 to 92 findings. Lexical modes are the closest: precise on real lexers, but its corpus evidence is one shell-lexing repository. Before restricting the loop to character or byte iteration it flagged separator flags such as ripgrep's `first` at equal rates in agent and ordinary code.

**The gate left correctness unchanged.**
- B2 matched B on every individual test status.
- B's eight extra passes over A all came from xjq.
- Every remaining failure was a spec reading that no lint rule can see: per-element grouping for `--text-all`, and an older backup destination scheme.

**Quality improved at no added cost.** B lowered erosion in every problem at slightly lower total cost than A, even though riprap never flagged complexity there. Over 90 percent of A's diagnostic findings were comments and READMEs. The gain therefore came from the agent working under a gate it ran itself, not from rules firing.

**Agents fixed findings themselves.** In all 26 gated checkpoints, the agent ran `riprap check` while it worked and finished with zero findings. The harness never had to resume it. Fixes included:
- deleting docstrings;
- replacing a mock of the agent's own module with a real test;
- moving README rationale into an ADR.

**Default ratchets traded size and cost for lower erosion.** B2 split every function above complexity 10 without breaking behaviour. The REST service's production code grew from 1,549 to 1,994 lines and from 15 to 43 files, xjq's verbosity doubled, and cost rose 31 percent over B. Its erosion gain is partly by construction, because complex-function mass and SCB erosion both weight complex functions by size.

**Limits.**
- One run per arm gives no error bars.
- Only Python was exercised.
- B2's xjq and file_backup runs used B's final scope adapter rather than B's original mounts.
- SCB's quality scorer includes the agents' own tests.
- SCB's snapshot extraction stripped A's bundled OPA binary of its execute bit. The scores above come from a permission-preserving re-evaluation.

## Open questions

- **Clone detection across languages.** Normalized syntax trees find renamed copies within a language; whether the model can find the same logic written in two languages is unknown and probably not worth it.
- **Rust swallowed errors.** The rule sees a `Result` only through a repository signature or a short list of standard calls, so it flags 1 of 23 statement-level discards and 10 of 792 `unwrap_or` calls in Tobias's repositories. Most of the rest discard channel sends, which fail only once the receiver hung up, or `Option`s that look the same without types.
- **Private state in tests for Rust and TypeScript.** Neither cell is built. The 10 TypeScript test files across the 12 repositories hold no bracket access, `as any` cast or suppression that could reach a `private` member, and dot access to one does not compile, so there is nothing to calibrate against. Rust unit tests read private fields only from inside the module, and telling the field from a same-named public field of another type needs the receiver's type. Matching by field name found 601 reads in orderready, mostly public fields of other structs such as `order.lines`. Binding the receiver to a constructor or type annotation in the same test found reads in 3 in-scope files, all in orderready. That binding also needs constructor return types, which riprap does not record.
- **Name-matched usage.** needless-export treats a Rust name as used outside its crate when a file outside uses it by path, call, import, attribute or macro argument. Counting only those uses recovered 9 of SCIP's 31 kasse additions and 4 of its 25 in stepkit-geometry; the rest collide with a same-named function or method in another crate, which syntax cannot tell apart without the receiver's type.
- **Trait and interface declarations.** anonymous-tuple checks functions with bodies, so a tuple in a Rust trait method or TypeScript interface signature without a body goes unchecked, although that declaration is where the tuple was chosen. Trait default methods count as imposed.
- **Comparison keys by name.** The anonymous-tuple exemption trusts the function name; `route_operation_sort_key` passes even though one caller destructures its result by position.
- **Recall in classes with external bases.** riprap treats every method of such a class as a possible override, so a dead helper in a unittest subclass passes. A per-framework list of hook names would close it.
- **Ratchets still reward splitting.** Splitting a complexity-20 function into two of complexity 10 drops complex-function mass to zero. Deletion no longer forces that reshuffle, but an agent may still choose it; the [erosion paper](agent-codebase-erosion.md) tests whether it does.
- **Handler recall.** A log-only handler that routes the error through a project's own reporting function counts as keeping it. Rust `.ok()` and `unwrap_or` count as discards on known `Result`s anywhere rather than as handlers outside a boundary, and `if let Ok` without `else` counts as neither.
- **Wildcard arms on own enums.** A Rust `_ =>` resolved to a closed repository enum in 128 production matches, and in 1 of orderready's 290. Single-variant projections and wildcards that reject or return nothing are safe to pass. The rest mixed real hidden cases, such as `_ => a >= b` standing for one comparison operator among thirteen, with general algorithms that are right for any variant, such as a numeric projection for every non-planar surface. Syntax cannot tell them apart, and the narrowest exact version, a wildcard covering exactly one variant, found 1 match across the 12 repositories. Python and TypeScript had almost no candidate matches.
- **String errors in published applications.** A package with binaries whose lib target nothing in the repository depends on passes, so a published crate whose library other repositories use is missed. riprap reads `publish`, description and license, but treats only packages without binaries as published libraries. Python and TypeScript still scope by boundary, so a script module outside every boundary is flagged whenever it throws from a named function.
- **Delegation-only Rust impls.** orderready's `DraftView` impl delegates every method to `self.screen`, the shape the delegation-only class form catches in Python and TypeScript. Rust impls are excluded from that form because newtypes and domain predicates that delegate one field were most of its first findings, so this case passes. The syntax alone does not separate a pass-through impl from a newtype.
- **SlopCodeBench rubric gaps.** The [rule phase](#results) found no shippable syntactic detector for the 27 rubric items riprap does not cover. Lenient parsing is the closest: Python handlers around parsing that return a default, and Rust deserialization through `.ok()` or `unwrap_or`, split sharply by class, but the hits read as deliberate parse-or-`None` helpers. A detector would need to know whether callers handle the absence. Specific-exception handlers that return a sentinel, and string comparisons of one field below three arms or spread across functions, remain the recall misses. The rubric's needless type wrappers pull against primitive-alias, which pushes toward newtypes.
- **Implicit state machines.** The [six candidate shapes](#results) need what syntax lacks: whether a field's sentinel is read as a real index, whether a stored flag is redundant with its payload, or whether parallel arrays share one lifecycle. Lexical modes split across flags is precise enough to retry once more lexers enter the corpus.
- **Single-file programs.** A stand-in that makes a benchmark's one program file the boundary silences every boundary-gated rule; treating it as core does not. Which is right depends on whether a single-file CLI has a core at all.
- **Residual corpus false positives.** forwarding-wrapper resolves some foreign methods to a same-named repository function, such as `s.trim()`, Prisma's `findUnique` and `Response.json`. literal-bool-argument flags serde's imposed `visit_bool`. radicale loads plugins through `import_module` on a variable with no package, leaving 17 unused files. 39 TypeScript files fall outside the grammar, and vite-plugin-react's example apps are copies of each other.
- **TypeScript coverage.** Only two of Tobias's repositories carry real TypeScript; the corpus adds zod, ky, vite-plugin-react, umami, shlink-web-client, jsoncrack and agent-written TypeScript, so most TypeScript evidence now comes from public code.
- **Default complexity cap on new code.** In the [SlopCodeBench comparison](#results), a default complex-function-mass of 0 kept every function at complexity 10 or below. It also grew one program by 29 percent in production lines and nearly tripled its file count. Whether a cap of 10 fragments new code systematically, or a higher per-function bar would keep the erosion gain at less size and cost, needs more than one run per problem.
- **Other standards.** Which external style guides to absorb after SlopCodeBench and Google's Rust guide, each rule passing the same acceptance run.

## References

- [ast-grep](https://ast-grep.github.io): fast tree-sitter pattern linter whose rules are short YAML files with separately tested valid and invalid examples. The base for language rules.
- [tree-sitter code navigation](https://tree-sitter.github.io/tree-sitter/4-code-navigation.html): per-grammar `tags.scm` queries that mark definitions and references, the mechanism behind GitHub's code navigation. A ready start on the model.
- [knip](https://knip.dev): finds unused files, exports and dependencies in JavaScript and TypeScript, with entry points declared per framework. The model for fact rules and entry-point config.
